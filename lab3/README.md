Локал, шууд JSON хариунд 25 мс нь хуваарилалтын хэлбэлзлийг багтаах хугацаа. Төлбөрийн 5% зориудын алдаанд 8% нь богино цонхны түүврийн хэлбэлзлийг тооцсон босго. Тайлангийн 200–400 мс хүлээлт дээр 50 мс боловсруулалтын зай үлдээсэн. Availability-ийн цагийн error budget нь 120 × (1 − 0.90) = 12 секунд. Хүсэлтийн budget нь нийт шалгалтын тооны 10%-ийн бүхэл хэсэг. Сэргэх хугацааг процессыг зогсоосон мөчөөс дараагийн анхны 200 хүртэл тусад нь хэмжинэ.

`node server.js` ажиллуулаад `k6 run slo-test.js` болон `k6 run slo-test-fail.js` команд ажиллуулна. Chaos ажиллуулалтад `k6 run --duration 2m slo-test.js` эхлүүлж, API-г 10 секунд таслаад дахин асаана. FAIL хувилбар тайлангийн замд p95 < 100 мс шаардана.

## Дүгнэлт

Сценариог threshold болгоход сэргэлтийн хугацаа ба хүсэлтийн амжилтын хувийг тусад нь тодорхойлох нь хамгийн их анхаарал шаардсан. Хэвийн ажиллуулалт дөрвөн босго давж exit 0 буцаасан. Chaos үед 5652 хүсэлтээс 4935 нь амжилттай буюу 87.31% байв. Хүсэлтээр тооцсон 565 алдааны budget-ийг 717 алдаа 152-оор хэтрүүлсэн. Анхны 200 хариу 11.054 секундэд ирсэн тул 12 секундийн сэргэлтийн зорилт биелсэн. Ажиллагаа тасрахад report-ийн хүлээлт алга болж, эвдрэлийн секунд тутамд илүү олон хүсэлт тоологдсон. Pay-ийн алдаа 4.12%-аас 15.55% болж reliability босгыг мөн зөрчсөн. Төлбөрийн reliability-г зөвхөн төлбөрийн үйлчилгээнд хүрсэн хүсэлтэд тооцож, холболтын алдааг availability-д хэмжиж болно.
